# 01 · 架构与模块划分

## 需求 → 技术目标的拆解

原始需求有三条：设置关注列表、名单内的人发新朋友圈时推送通知、点通知跳到对应朋友圈。
把它翻译成可验证的技术目标：

| 编号 | 目标 | 验证方式 |
|---|---|---|
| G1 | 能设置并持久化一个「关注好友 wxid 集合」 | 本地逻辑验证：写入后重读一致（`tools/verify`） |
| G2 | 能在微信把一条新朋友圈写入本地库的那一刻捕获到它 | 真机验证：发一条动态观察日志出现「命中关注对象」 |
| G3 | 能从名单中筛出应提醒的动态（不多、不漏、不重复） | 本地逻辑验证 71 项断言 + 真机验证 |
| G4 | 能弹出系统通知，且点击后落到那条具体的朋友圈 | 真机验证：点击通知观察落点页面 |
| G5 | 插件卸载后不留残留（Hook 全部释放） | 本地验证句柄清空 + 真机验证卸载后无异常 |

## 架构选择

### 为什么是「Hook 本地数据库写入」

捕获新朋友圈有四条备选路径，逐一评估：

| 方案 | 可行性 | 问题 |
|---|---|---|
| **A. Hook WCDB `SQLiteDatabase` 写入方法** | ✅ 选用 | 依赖的只有方法名与表名字符串，跨版本稳定 |
| B. Hook 微信网络层 `NetSceneSnsSync` 的回调 | ⚠️ | 解析 protobuf 需要混淆类名与 DexKit，版本敏感 |
| C. Hook `SnsInfoStorage` 的插入逻辑 | ⚠️ | 类名混淆，需要 DexKit 匹配特征字符串 |
| D. 轮询读取 `SnsMicroMsg.db` 文件 | ❌ | 需要文件访问权限；进程常驻时数据库被独占；无实时性 |

选 A。关键在于：**朋友圈数据最终一定要以 `INSERT` 的形式落进 `SnsInfo` 表**，
而 `SQLiteDatabase.insert(String table, String nullColumnHack, ContentValues values)`
的方法名、参数顺序、表名字符串都不受代码混淆影响。这条路径比 Hook 微信业务类稳定得多。

代价是拿到的是 `ContentValues` 而不是 `SnsInfo` 对象：

- 能直接读到的：`snsId`、`userName`、`createTime`、`type`（都是 `SnsInfo` 表的真实列名）。
- 读不到的：正文。`content` 列是 protobuf BLOB，直接转字符串没有意义。
  需要复用微信自己的 `SnsInfo.convertFrom(ContentValues)` + `getTimeLine().ContentDesc` 解码，
  这一步失败不影响提醒，只影响通知正文里的摘要。

### 为什么通知要自己发

WA 提供了 `notify(String title, String text)`，但它**不能自定义点击行为**，
无法满足「点通知跳到对应那条朋友圈」。所以用 `NotificationManager` 自己构造通知：

- 建独立通知渠道 `momentwatch_new_post`，`IMPORTANCE_HIGH`；
- `setContentIntent(PendingIntent.getActivities(...))` 挂上跳转链；
- 通知 ID 用 `snsId` 哈希，保证同一动态复用同一条通知，不同动态互不覆盖。

## 分层与模块划分

遵循 WA 官方的[分层建议](https://github.com/HdShare/WAuxiliary_Plugin/blob/main/wauxiliary-plugin-dev/references/architecture.md)：
`main.java` 只保留模块加载与 WA 回调转发；具体职责全部下沉到模块。

```
                     ┌──────────────────────────────┐
                     │        main.java（入口）      │
                     │  loadJava 顺序 / WA 回调转发  │
                     │        （无状态、无业务逻辑）  │
                     └───────────────┬──────────────┘
                                     │
   ┌─────────────────────────────────┼─────────────────────────────────┐
   │                                 │                                 │
   ▼                                 ▼                                 ▼
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ Util     │──▶│ Config   │──▶│ Jumper   │──▶│ Notifier │──▶│ SnsHook  │──▶│SettingsUi│──▶│ Service  │
│ 通用工具 │   │ 配置状态 │   │ 跳转组装 │   │ 通知发送 │   │ Hook+判定│   │ 设置界面 │   │ 生命周期 │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

箭头既是**加载顺序**，也是**允许的调用方向**：每个模块只能调用它左侧已加载的模块，不允许反向或循环依赖。
`Service` 放在最后，因为它要能调用所有模块；`Util` 放在最前，因为它不依赖任何业务状态。

### 各模块职责与边界

| 模块 | 职责 | 明确不做 |
|---|---|---|
| `Util` | 文本清洗、集合解析、时间格式化、主线程 Toast、统一日志前缀 | 不碰配置、不碰 WA 对象 |
| `Config` | 配置与运行状态的内存模型；读写 `config.prop`；去重账本与淘汰 | 不做判定、不做 UI |
| `Jumper` | 构造跳转 Intent 链与三级降级 | 不发通知、不碰数据库 |
| `Notifier` | 构造并发出通知（渠道、文案、`PendingIntent`） | 不决定「要不要发」（由 `SnsHook` 决定） |
| `SnsHook` | Hook 注册/卸载；解析 `ContentValues`；命中判定与去重 | 不构造通知内容、不构造 Intent |
| `SettingsUi` | 设置界面与好友多选；收集用户输入 | 不直接写 `config.prop`，一律走 `Config` |
| `Service` | 生命周期：`onLoad` 载入配置、重置监视起点、注册 Hook；`onUnload` 释放 | 不含业务逻辑 |

### 为什么这样切

- **配置读写与界面分离**：`SettingsUi` 只收集输入，落地交给 `Config`。
  这样界面改版不会影响配置格式，配置格式变更也不会散落到 UI 代码里。
- **判定与通知分离**：`SnsHook` 只回答「要不要提醒」，`Notifier` 只回答「怎么提醒」。
  想加一条过滤规则只改一个文件，想换通知样式也只改一个文件。
- **跳转独立成模块**：跳转是整个插件里**最版本敏感**的部分，单独隔离便于降级与后续适配。
- **可复用的解析函数尽量只吃普通值**：`SnsHook` 里所有解析函数接收 `ContentValues` / `Object[]`，
  Hook 回调参数只在 `mwSnsHandleHookParam` 里用反射拆解一次，因此可以在 JVM 上用桩对象直接测。

## WA 运行时约束（设计前提）

这些约束来自 WA 官方插件开发文档，直接决定了代码风格：

1. **BeanShell 顶层脚本**：`.java` 文件不是类，顶层可以写语句、变量、函数、import。
2. **共享命名空间**：所有模块在同一个解释器里执行，顶层函数名会互相覆盖 →
   本项目所有顶层符号都带模块前缀（`mwUtil*` / `mwConfig*` / `mwJump*` / `mwNotify*` /
   `mwSns*` / `mwHook*` / `mwUi*` / `mwService*`），并通过脚本校验确认无重名。
3. **`loadJava` 的相对路径以 `pluginDir` 为基准**，被依赖的模块必须先加载。
4. **Hook 必须在 `onUnload` 里释放**：注册时保存返回的句柄，卸载时逐个 `unhook()` 并清空。
5. **必需文件只有 `info.prop` 与 `main.java`**；`config.prop` 由配置接口在首次写入时生成，
   因此不预置该文件。
6. **不能引用 `de.robv.android.xposed.*` 下的类型**：WA 默认开启「Xposed API 调用保护」，
   脚本里命名 `XC_MethodHook` 这类类型会让整个插件加载失败。Hook 必须走 WA 内置接口，
   且回调参数用反射读取。详见 [04-detection-and-jump.md](04-detection-and-jump.md) 1.2.1。

## 可测试性设计

把可测的部分与不可测的部分隔离开：

- **可测（本地 JVM）**：工具函数、配置读写、命中判定、去重、时效、参数解析、跳转组装、
  Hook 注册与回调链路、Hook 生命周期。
  这些代码只依赖普通值 + 少量桩得出来的接口（`ContentValues` / `Intent` / WCDB 写入方法集合），
  因此 `tools/verify` 能用 71 项断言在本地跑通 —— 包括用桩类和伪回调参数端到端驱动一次"新动态落库"。
- **不可测（必须真机）**：Hook 是否真的拦到微信的写入、通知是否真的弹出、点击是否真的落到正确页面、
  好友多选的交互。这些依赖宿主行为，列入 [06-test-plan.md](06-test-plan.md)。

## 与非目标

明确划出界限，避免功能蔓延：

- 不做自动点赞 / 评论 / 转发 / 发圈 —— 本插件的价值是「提醒」，不是「代操作」。
- 不做动态内容的服务端分析、不去重聚合、不做关键词过滤。
- 不做主动后台刷新朋友圈 —— 那需要 DexKit 匹配混淆类名，属于版本敏感且代价高的能力，
  当前版本依赖微信自身的同步（限制已写入 README「已知限制」）。
- 不做多账号区分 —— 插件当前只服务当前登录账号。
