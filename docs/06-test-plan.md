### 已修复问题（2026-10-05 真机第一轮）

| 现象 | 根因 | 修复 |
|---|---|---|
| 加载 `[MomentWatch]` 失败，插件被自动关闭 | 脚本里命名了 `de.robv.android.xposed.XC_MethodHook`，而 WA 默认开启「Xposed API 调用保护」，插件脚本的命名空间里没有该类型 → `Class: XC_MethodHook not found in namespace` | 改用 WA 内置 `hookAfter` / `unhook`；回调参数不声明类型，`args` / 返回值 / 方法名全部用反射读取 |

排查依据：LSPosed 日志中本插件报 `Plugin[MomentWatch]: load Failed: ... Class: XC_MethodHook not found in namespace`，
堆栈指向声明处；同时社区插件「僵尸粉检测」在同版本上报 `Unknown class: XC_MethodHook`，交叉印证了是
WA 的保护机制而不是本插件独有问题。详见 [04-detection-and-jump.md](04-detection-and-jump.md) 1.2.1。

## 三、真机测试清单

### 前置

- [ ] 已安装 LSPosed（或同类框架），作用域勾选微信并**已重启微信**
- [ ] 把 `MomentWatch` 目录放进 WA 插件目录，在 WA 里加载本插件
- [ ] 打开插件日志区域（WA 的插件日志页），准备观察日志

### P0 · 必测（不通过则功能不成立）

#### T1 插件能正常加载

- **操作**：加载插件后看日志。
- **预期**：出现 `[MomentWatch] 已加载：关注 0 人，时效 24 小时内，Hook N 个方法`，且 `N > 0`。
- **失败排查**：
  - 出现 `已自动关闭` 或 `load Failed` → 先看错误里有没有 `XC_MethodHook` / `XposedBridge`，
    有的话说明又引入了 Xposed 类型名（本插件的硬性约束见
    [04-detection-and-jump.md](04-detection-and-jump.md) 1.2.1）；
  - `N == 0` → 见 [03-interfaces.md](03-interfaces.md) 第 2.1 节，确认 WCDB 类名；
  - 完全没有本插件日志 → 检查插件目录名与 `info.prop` / `main.java` 是否存在、大小写是否正确。

#### T2 设置界面能打开、能选人、能保存

- **操作**：打开插件设置 → 点「关注名单」→ 筛选某个好友 → 勾选 → 保存 → 关掉再打开。
- **预期**：好友列表能读出；保存后回到主页，关注名单显示「已关注 N 人」；重开设置后仍是 N 人。
- **失败排查**：列表空 → 好友列表读取失败，看日志 `读取好友列表失败`；
  保存后人数不对 → 看筛选后的「全选」是否只作用于当前筛选结果（这是刻意设计）。

#### T3 能捕获到关注对象的新动态

- **操作**：用关注名单里的某个账号发一条朋友圈（或让该好友发一条），等待并观察日志。
- **预期**：出现 `[MomentWatch] 命中关注对象: user=... snsId=... localId=... create=... type=...`。
- **失败排查**：完全没有 → 微信可能尚未把该动态写入本地库，先手动刷新一次朋友圈再看；
  仍没有 → 检查是否在时效窗口内（`create` 是否早于 `now - 时效`），或该 `snsId` 是否已在去重账本里。

#### T4 通知能弹出且文案正确

- **操作**：接 T3。
- **预期**：弹出系统通知，标题形如「张三 发布了图文动态」，正文为动态文字摘要或「点击查看该朋友圈」。
- **失败排查**：有 `命中关注对象` 但没有 `已发出通知` → 看是否有 `发出通知失败` 日志；
  通知被系统拦截 → 检查微信的通知权限与本插件创建的通知渠道 `朋友圈关注提醒` 是否被关闭。

#### T5 点击通知能落到**那条**朋友圈（最高风险项）

- **操作**：点 T4 的通知。
- **预期**：微信打开，**直接停在对应那条朋友圈的详情页**。
- **同时确认日志**：`[MomentWatch] 跳转模式=精确 localId=<正数>`。
- **失败排查**：
  - 落到朋友圈首页 → `localId` 没取到（日志里 `localId=-1`），见 [04](04-detection-and-jump.md) 1.4；
  - 落到该作者朋友圈但不是那一条 → `localId` 取到了但详情页语义不同，属版本适配问题；
  - 落到**别人的**动态 → 同上，属高危，必须修正后再发布；
  - 微信没被拉起 → 组件名不存在，检查 `SnsCommentDetailUI` / `LauncherUI`。

#### T6 卸载后无残留

- [ ] 在 WA 里卸载/停用插件，观察日志出现 `已卸载 N 个 Hook`
- [ ] 之后正常使用微信（收发消息、刷朋友圈、点赞评论）不出现闪退或卡顿
- [ ] 重新加载插件，功能仍可用

### P1 · 重要功能项

#### T7 去重：同一条动态只提醒一次

- **操作**：接 T3，什么都不做，多等几分钟，期间手动刷新几次朋友圈。
- **预期**：同一条动态不再产生第二条通知。
- **失败排查**：日志里重复出现同一 `snsId` 的 `命中关注对象` → 去重账本异常，检查 `mw_seen_ids` 落盘。

#### T8 历史动态不刷屏

- **操作**：清空已提醒记录 → 在 WA 里重新加载插件 → 立刻打开朋友圈（触发整页同步）。
- **预期**：不会因为页面里的历史动态而产生一批通知（日志里对旧动态会因监视起点被跳过）。
- **失败排查**：出现一批通知 → 检查 `createTime` 是否取到（取不到时不做时间过滤，是刻意行为）。

#### T9 提醒时效生效

- **操作**：把时效设为 6 小时；把一条超过 6 小时的动态"制造"成新写入（例如清空记录后重载插件，
  再让好友转发一条老动态的图片作为新发布，或直接用一条刚发的动态做对照）。
- **预期**：时效窗口内的提醒，窗口外的不提醒。
- **失败排查**：都不提醒 → 时效被设成了极小值；全部提醒 → 检查 `mw_max_age_sec` 是否为 0（不限）。

#### T10 总开关生效

- **操作**：关掉「启用提醒」，让关注对象发一条动态。
- **预期**：日志里连 `命中关注对象` 都不出现（总开关在判定最前面）。
- **说明**：Hook 仍在运行，只是不做任何处理，避免反复注册/卸载。

#### T11 测试通知可用

- **操作**：设置里点「发送测试通知」。
- **预期**：立刻收到一条测试通知，点击后至少能打开朋友圈相关页面（测试通知没有真实 `snsId`，
  因此会走降级路径，这是预期行为）。

#### T12 名单边界

- [ ] 关注名单为空 → 不产生任何提醒，日志有提示
- [ ] 名单里手动写入一个不存在或非好友的 `wxid` → 不影响其他条目
- [ ] 名单里混入换行/全角逗号 → 仍能正确解析（容错设计）

### P2 · 稳定性与观感

- [ ] 连续 24 小时挂着，观察微信是否异常耗电、发热、卡顿
- [ ] 通知点击后返回键能正常回到微信主界面（而不是卡在孤立页面）
- [ ] 深色模式下设置界面文字可读（界面用固定浅色卡片，与系统主题无关）
- [ ] 好友数量很多（500+）时，好友多选界面能打开且滚动流畅
- [ ] 微信被系统杀掉后重新打开，插件仍能正常提醒（账本已落盘）

## 四、验收标准

功能验收按 P0 全通过判定：

| 编号 | 标准 |
|---|---|
| A1 | 插件加载后日志显示 Hook 到 ≥1 个方法 |
| A2 | 能设置并持久化关注名单 |
| A3 | 关注对象发新动态时能捕获并推送通知 |
| A4 | 点通知能落到**对应那条**朋友圈详情页 |
| A5 | 卸载后无残留、微信无异常 |

P1 / P2 作为质量项，允许存在已记录的偏差，但需在 README「已知限制」中体现。

## 五、回归方式

改动插件后：

```bash
bash tools/verify/run.sh
```

- 解析校验失败 → 该文件在真机上会加载失败，必须修；
- 断言失败 → 要么是逻辑回归，要么是预期行为变了（后者需要同步更新本文档与
  [01](01-architecture.md) / [03](03-interfaces.md)）。

改完涉及真机的部分（Hook 点、跳转组件、组件 extra）后，**必须重跑 T3 / T4 / T5**，
这三项是唯一无法本地覆盖的链路。
